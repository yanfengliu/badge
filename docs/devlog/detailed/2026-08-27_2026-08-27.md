## The suite stopped flipping coins under load

**Why now:** the navigation session's critic measured the full suite as green only about one run in three while other work shared the machine, always in untouched files that passed in isolation; the owner spun the follow-up off as its own task.

**What was believed and proved false:** the flake was first read as "two slow tests need longer timeouts like their siblings." Reproducing it deliberately showed two distinct mechanisms, and the named `renameAttempts` failure was not slowness at all: the test's own real `rename` inside its hook can hit a genuine transient Windows denial under load, the production loop correctly retries, and the pinned `toBe(1)` then fails while the behavior under test is exactly right. Pinning one interference-free interleaving on a live filesystem measures the weather, not the code.

**Calibration mattered:** a 32-process full-oversubscription spin load produced 13 timeout failures — including one test already at 60 seconds — which is a machine-wide denial of service, not the reported condition; that run was kept only as a census of the load-sensitive class. The proof standard was set at a 16-process spin load (one extra full workload, 84–99% total CPU), which reproduced the reported 1-in-3 flake before the fix and passed three consecutive full runs after it.

**Shape of the fix:** live-filesystem gates now assert what the publish and lock loops guarantee under any interleaving — the simulated denial's retry happened (lower bound), attempts stay within the shared `TRANSIENT_WINDOWS_RENAME_ATTEMPTS` ceiling, and (new, exact under load) no rename attempt ever observes an already-published output tree; one cause assertion accepts any transient Windows denial because a real read denial can legitimately become the recorded last error. The heavy gate class — `windowsIt` PowerShell System.Drawing decoders, multi-hundred-asset decode-and-hash sweeps, the whole-repo TypeScript sweep, and the 184-prompt catalogue-studies binder — got 60-second budgets; the deliberate 4-second startup-validation performance budget was deliberately left alone. The `it.each` persistent-denial bounds test kept its exact `toBe(8)` because its hook throws before any real filesystem work, so its count is structural.

**Validation:** the two originally named files pass in isolation and stayed green through every loaded run from the first fix onward; the full 157-file suite then passed three consecutive runs at 84–99% CPU. Register entry: “The full test suite was a coin-flip instrument under parallel CPU load.”

**Independent critic result:** confirmed no accidental-regression path survives the relaxed assertions — flipped ambiguity resolution is double-caught by the new invariant counter plus an ENOENT rejection, no-retry and budget-change regressions fail the retained `/after 8/` messages and the structurally exact `toBe(8)` counts, and vitest’s third-argument timeout form was proved effective empirically. Two honest residuals: a deliberate rollback-and-republish rewrite (new un-publish code, unreachable by accident) would satisfy the new invariant where the old `toBe(1)` would not, and far narrower flake windows remain in the file’s unchanged exact cause-identity assertions, so this fix removed the dominant flake class rather than every conceivable one.

**Why now:** the owner reported two navigation dead ends in one sitting: a Collection shelf click lands in Discover with no way back, and left/right arrow keys move between badges of the same set nowhere — both now registered in `docs/learning/defect-register.md` with their gates.
